# 글쓰기 톤 & 포맷 가이드

## 대표 모범 사례 (2026-11-09 지정)

**[AI가 물어보면 채팅 대신 HTML로 답한다](../src/content/posts/Devops-Automation/ai-agent-decision-html.md)**
— 공개: https://kmsk99.github.io/post/ai-agent-decision-html/ · 네이버판 https://blog.naver.com/masonnote/224470919712

사용자가 "가장 좋은 블로그 글"로 지정했다. 새 글은 이 글을 기준으로 쓴다. 이미 공개된 예전 글은 고치지 않는다(2026-11-10 결정). 판단이 갈리면 아래 규칙보다 이 글 자체를 먼저 본다.

### 이 글에서 가져올 것

**제목**
- 콜론으로 두 동강 낸 제목, "~한 방법", "쏟아졌다" 같은 과장은 AI 느낌이 나서 쓰지 않는다. 하는 일을 담백한 한 문장으로. (예: "AI가 물어보면 채팅 대신 HTML로 답한다")

**시작**
- 강한 사실 하나로 연다. 숫자가 있으면 숫자로. ("정해야 할 것 13개를 5분도 안 돼서 다 정했다.")
- 바로 뒤에 "처음부터 이랬던 건 아니다"로 과거와 대비시켜 이야기를 연다.
- 인사·"오늘은 ~를 얘기해 볼게요"·자기소개·메타 도입 금지.

**흐름 — 후킹 → 상황 → 문제 → 시도와 수정 → 결과·한계**
- 해결책을 바로 주지 않는다. 방법이 단계별로 어떻게 바뀌었는지 보여 준다. (채팅 질문 → HTML 설명서 → 번호로 답하기 → 누르고 복사하기)
- 단계마다 "그런데 이게 또 문제였다"로 다음 단계로 넘어간다.

**독자와 말투**
- 내 경험은 한다체 '~했다'. 짧은 문장, '그래서/그런데' 리듬.
- 독자는 끝까지 2인칭 **'당신'**으로 부른다. '여러분' 금지. 섹션마다 한 번쯤 "당신도 ~했다면"으로 독자를 끌어온다.
- 소제목은 질문형. ("왜 정할 게 자꾸 쌓일까?", "누구에게나 필요한 방법일까?")
- 인터뷰에서 들은 구어 말투를 그대로 옮기지 않는다. 내용은 살리되 문장은 다시 쓴다.

**쉽게 — 중학생도 읽히게**
- 풀어 쓸 것은 **상황·과정·이유**다. 내부자만 아는 맥락을 일상 비유로 바꾼다. (개편 중 새 제약 → 벽을 허물었더니 배관, 미뤄 둔 결정 → 안 낸 숙제, 선택지 페이지 → 객관식 시험지와 답안 칸)
- 독자가 이미 아는 말은 설명하지 않는다. AI 에이전트, 바이브코딩, HTML, Claude Code, Codex 같은 것.
- 막연한 질문 대신 구체적인 예시 질문을 보여 준다. ("로그인은 처음부터 받을까요, 나중에 받을까요?")

**근거와 화면**
- 숫자·시간·횟수는 실제 기록에 있는 것만 쓴다. 지어내지 않는다.
- 고객사·실무 화면은 싣지 않는다. 같은 구조로 가상 예시를 만들고, 그림 설명에 "가상의 예시"라고 밝힌다.
- 독자가 직접 해 볼 수 있으면 해 볼 수 있게 둔다. (예시 페이지를 `/demos/`에 올려 링크, 프롬프트는 본문에 그대로 공개)

**끝**
- "누구에게나 필요한가?"로 한계를 한 번, 평범한 말로 밝힌다. (추천을 그대로 따르는 사람은 안 써도 된다)
- 마지막은 독자가 다음에 할 행동 한 줄로 끝낸다. 구독 요청·교훈 나열·"다음 글에서" 예고는 하지 않는다.

### 만드는 순서

1. 독자의 질문 하나를 정한다. (첫 독자: 1인으로 앱·사업을 시작하는 개발자)
2. 작성자를 인터뷰한다. 무엇이 힘들었는지, 왜 그렇게 바꿨는지, 이 방법이 안 맞는 사람은 누구인지.
3. 실제 기록(세션 로그·커밋·메일)에서 시각과 숫자를 확인한다.
4. 위 기준으로 초안을 쓰고, 처음 보는 사람 입장에서 다시 읽는다. 어려운 건 용어가 아니라 빠진 맥락이다.

## 기존 가이드 (모범 사례와 어긋나면 모범 사례를 따른다)

## 페르소나
- 실무 중인 1인칭 개발자 시점, 솔직한 감정과 생각을 드러내며 대화하듯 작성.
- 해요체/합니다체 혼용 가능하되 일관된 톤 유지, 영어 기술 용어는 자연스럽게 사용.

## 전개 흐름
1) 문제 상황·불편함으로 도입, 왜 이 선택을 했는지 배경/목표/대안 제시  
2) 구현: 핵심 아이디어 → 주요 단계 → 예상치 못한 이슈와 해결  
3) 마무리: 결과, 교훈, 다음 계획, 독자에게 질문/피드백 요청

## 포맷팅
- 문서 맨 위 프론트매터: `title`, `created`, `modified?`, `tags?`, `summary?`
- 본문은 `# Intro` 또는 `##`로 시작해 흐름을 잡고, 단계는 번호/리스트 적극 활용.
- 코드 블록에는 언어 라벨과 의도 주석을 짧게 추가.
- 이미지 자리표시자는 `![[file.png]]`를 사용하고, Reference 섹션을 마지막에 둡니다.

## 체크리스트
- 1인칭 시점과 말투가 끝까지 유지됐는가?
- 재현 가능한 코드/설정을 넣었는가?
- 교훈·다음 개선 아이디어·참고 자료를 빠뜨리지 않았는가?
- 독자가 시도해볼 과제나 질문을 남겼는가?
