15초짜리 1080p 영상 한 편을 만드는 데 6분 7초가 걸렸다.

GPU 서버를 시간당 2.24달러에 빌렸으니 영상 한 편에 0.23달러가 든 셈이다. 게다가 이 서버 비용은 가지고 있던 AWS 크레딧으로 냈다. 실제로 내 주머니에서 나간 돈은 거의 없다.

물론 처음부터 이렇게 잘 돌아간 건 아니다. 첫 번째로 빌린 서버는 영상 한 편도 만들지 못하고 멈춰 버렸다.

(2026년 11월 14일 AWS 미국 동부 리전에서 직접 잰 값이다. 가격과 모델 구성은 바뀔 수 있다.)

## 왜 힉스필드 대신 직접 돌렸을까?

이유는 하나다. 비쌌기 때문이다.

힉스필드는 여러 회사의 영상 모델을 크레딧 하나로 묶어 쓸 수 있게 해 주는 서비스다. 요금제는 월 19달러부터 258달러까지 있다. 1080p 10초 영상을 만들 때 차감되는 크레딧을 돈으로 환산해 보면 Kling 3.0은 0.53~0.79달러, Seedance 2.0은 약 2.97달러다. 쓰고 남은 구독 크레딧은 다음 달로 이월되지도 않는다. (2026년 10월 11일 공식 요금제 페이지 기준, 세금 별도)

그러다 MiniMax의 영상 모델인 H3가 가중치까지 공개돼 있다는 걸 알게 됐다. 가중치가 풀렸다는 건 내 서버에서 직접 돌릴 수 있다는 뜻이다.

한 유튜브 영상에서는 RunningHub라는 중국 클라우드 서비스로 15초 1080p 영상을 한 편에 100원 정도면 뽑는다고 소개했다. 그래도 나는 AWS를 택했다. 쓰다 남은 AWS 크레딧이 넉넉했기 때문이다. 크레딧으로 서버를 빌리면 거의 공짜나 다름없다.

## MiniMax H3는 어떤 모델일까?

글이나 이미지를 넣으면 영상과 스테레오 소리까지 한 번에 만들어 주는 모델이다. 길이는 4초에서 15초까지, 초당 24프레임으로 나온다.

모델 크기는 33B다. 영상을 만드는 본체와 글을 읽는 부분만 합쳐도 40GB에 달한다. 처음에는 메모리 24GB로도 돌릴 수 있다는 글을 보고 맥에서 돌려 볼까 싶었지만, 현실적이지 않다는 걸 금방 깨달았다. 결국 GPU 서버를 빌리기로 했다.

공개된 가중치는 기본 해상도 768p 모델뿐이다. 공식 2K 모델은 API로만 쓸 수 있다.

모델은 ComfyUI로 돌렸다. ComfyUI는 모델 불러오기, 영상 만들기, 저장하기 같은 단계를 블록처럼 이어 붙여 작업 흐름을 짜는 프로그램이다.

## 첫 서버는 왜 멈췄을까?

처음에는 g6e.xlarge를 빌렸다. 48GB짜리 L40S GPU가 달린 서버라 충분할 줄 알았다.

그런데 GPU가 아니라 일반 메모리(RAM)가 문제였다. 이 서버의 RAM은 30GB였는데, 모델을 올리는 도중에 메모리가 바닥나 프로그램이 강제로 꺼졌다. 디스크 일부를 메모리처럼 쓰는 스왑을 32GB 붙여 봤지만 상황은 오히려 더 나빠졌다. 7분 넘게 준비 단계에서 꼼짝도 하지 않더니 원격 접속까지 끊겨 버렸다.

그래서 GPU는 그대로 두고 RAM만 64GB로 늘린 g6e.2xlarge로 바꿨다. 요금은 시간당 2.24달러다. 15초 영상을 만드는 동안 RAM 사용량을 확인해 보니 42GB를 쓰고 있었다. 30GB짜리 서버로는 애초에 무리였던 셈이다.

빈 서버가 없을 때도 있었다. 같은 날 미국 동부 리전의 가용 영역 네 곳에 모두 요청을 넣었지만, 전부 "재고 없음"이 뜨며 실패한 적도 있다.

64GB 서버로 옮긴 뒤에도 한 번 더 막혔다. 첫 영상의 그림은 4분 50초 만에 다 만들어졌는데, 마지막에 소리를 만드는 단계에서 오류가 났다. 서버 기본 이미지에 미리 깔려 있던 라이브러리 경로가 버전 충돌을 일으킨 것이다. ComfyUI를 띄울 때 그 경로를 빼 주니 해결됐다.

## 모델 40GB는 어디에 넣어 둘까?

서버는 쓸 때만 빌리고 다 쓰면 끈다. 그러다 보니 서버를 켤 때마다 모델 40GB를 새로 준비해야 했다.

처음에는 서버 이미지(AMI)에 모델까지 통째로 구워 두는 게 가장 빠를 줄 알았다. 이미 디스크에 들어 있으니 따로 내려받을 필요가 없다고 생각했기 때문이다.

결과는 정반대였다. 이미지로 복원한 디스크는 파일을 처음 읽을 때 원본 저장소에서 조금씩 가져오는 방식이라, 읽는 속도가 초당 30MB 남짓에 불과했다. 이 속도면 40GB를 다 읽는 데만 20분 넘게 걸린다.

비교해 보니 다른 방법이 훨씬 빨랐다.

- 서버 이미지에서 처음 읽기: 4분 가까이 지나도 끝나지 않아 중단했다
- 허깅페이스에서 새로 받기: 92초
- 같은 리전의 S3 저장소에서 여러 갈래로 나눠 받기: 63초

그래서 서버 이미지에는 프로그램만 남기고 모델은 S3에 넣어 뒀다. 서버를 켜면 S3에서 모델을 내려받는 동시에, 이미지에 남은 프로그램 폴더 7GB를 잘게 쪼개 미리 읽어 둔다. 이렇게 바꾸니 서버를 켜고 생성 준비를 마치기까지 3분 30초면 충분했다.

## 15초 1080p를 어떻게 6분에 만들었을까?

처음 돌려 본 기본 설정은 20단계를 거쳐 768p 영상을 만드는 방식이었다. 5초짜리 하나를 만드는 데 모델 로딩까지 포함해 519초가 걸렸다.

![7+1 방식으로 만든 15초 1080p 영상의 한 장면. 생성에 367초가 걸렸다](/images/minimax-h3-aws/fig-rooftop-15s.jpg)

속도를 높이려고 단계를 8번으로 줄인 터보 설정을 써 봤다. 5초 영상은 생성 시간이 127초로 확 줄었다. 그런데 길이를 15초로 늘리자 826초나 걸렸다. 영상 길이는 3배가 됐는데 한 단계를 처리하는 시간은 14초에서 98초로 7배나 늘어난 것이다. 영상이 길어지면 모든 프레임이 서로를 참고하느라 계산량이 급격히 불어나기 때문이다.

결국 찾은 해답은 '7+1' 방식이었다. 유튜버 Deno가 공개한 작업 흐름을 내 환경에 맞춰 고쳐 썼다.

1. 960×544 저해상도에서 8단계 중 7단계를 먼저 끝낸다.
2. 완성된 그림이 아니라 그림이 되기 직전의 데이터만 2배로 키운다.
3. 1920×1088 고해상도에서 마지막 1단계만 처리한다.

무거운 작업은 대부분 작은 화면에서 먼저 끝내 버리는 원리다. 덕분에 15초 1080p 영상이 367초 만에 나왔다. 터보 768p로 만들 때보다 두 배 이상 빨라졌고 해상도도 더 높아졌다. 마침 RunningHub를 소개한 영상에서 말한 "15초 1080p에 6분"과 걸린 시간이 거의 같았다.

![같은 서버(g6e.2xlarge)에서 설정별로 잰 시간과 영상당 서버 비용. 비용은 시간당 2.24달러로 계산한 값이다](/images/minimax-h3-aws/fig-cost-table.png)

## 켜고 끄는 건 어떻게 할까?

맥에서 명령 한 줄이면 끝난다.

./h3.sh run "프롬프트" 15

이 명령 하나로 서버를 켜고, 모델을 내려받고, 15초 영상을 만들어 내 맥으로 가져온 뒤 서버까지 끈다. 중간에 오류가 나도 서버는 알아서 꺼지도록 만들었다. 깜빡하고 서버를 켜 두는 게 가장 큰 돈 낭비이기 때문이다.

5초 영상으로 처음부터 끝까지 한 번 돌려 보니 521초가 걸렸다. 서버 비용은 약 0.3달러였다. 15초 영상은 10분 남짓 걸리고 0.37달러 안팎이 든다.

여러 편을 만들 때는 서버를 한 번만 켜 두고 생성 작업만 연달아 돌린다. 서버를 켜는 데 드는 3분 30초를 처음에 한 번만 쓰면 된다.

![명령 한 줄이 하는 일. 켜기부터 끄기까지 자동으로 이어진다](/images/minimax-h3-aws/fig-flow.png)

## 결과물은 쓸 만했을까?

솔직히 품질은 조금 아쉽다.

특히 한글은 거의 안 된다. 서울 골목에서 할아버지가 고양이에게 간식을 주는 장면을 만들어 봤는데, 화면 속 간판 글자가 하나같이 뭉개져 나왔다. 얼핏 한글처럼 생겼지만 읽을 수 있는 글자는 하나도 없다.

![서울 골목 시험 영상의 한 장면. 사람과 고양이는 그럴듯하지만 간판 글자는 읽을 수 없다](/images/minimax-h3-aws/fig-alley-hangul.jpg)

그런데도 계속 쓰는 이유는 싸고 빨라서다. 15초 1080p를 6분 만에 뽑아낸다는 건 예상보다 훨씬 빠른 속도였다. 한 편당 서버 비용이 1달러도 안 되니 마음에 들 때까지 여러 번 다시 만들어도 부담이 없다.

## 누구에게 맞을까?

모든 사람에게 맞는 방법은 아니다.

힉스필드처럼 여러 회사의 모델을 골라 쓰는 편리함은 없다. 직접 서버를 빌리고, 재고가 없으면 다른 곳을 찾고, 메모리가 터지면 원인을 찾아야 한다. 나는 이 과정을 AI 코딩 에이전트에게 맡겨 처리했지만, 그런데도 한나절이 걸렸다.

반대로 AWS 크레딧이 남아 있거나 영상을 아주 많이 뽑아야 한다면 직접 돌려 볼 만하다. 서버와 데이터, 자동화를 모두 내가 쥐게 된다.

어느 쪽이 나을지 고민된다면 먼저 계산부터 해 보자. GPU 서버의 시간당 가격에 영상 한 편을 만드는 데 걸리는 시간을 곱하면, 내 영상 한 편의 원가가 나온다.
